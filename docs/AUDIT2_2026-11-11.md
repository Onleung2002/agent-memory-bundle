### WEAKNESS (defense-in-depth gaps)

**W1 (surface 1, MEDIUM-LOW). Small-order / non-canonical point acceptance gives a zero-private-key forgery primitive.**
`mbcp/_ed25519.py:138-147` `_decode_point` performs no `y < q` canonical-encoding check and no small-order/cofactor check; `checkvalid` (`mbcp/_ed25519.py:200-229`, cofactored equation at :48) accepts the identity point B (y=1). Consequence, demonstrated live (`/tmp/audit2/probe2b_identity_chain.py`): with the **identity pubkey** (bytes 0x01||0x00*31) a pack/receipt signature is `(R=B, S=1)` - forged with **zero secret material** - and `checkvalid` accepts it. End-to-end intake chain (`probe2b` CHAIN check): operator lists the identity pubkey in `.mbcp.authorized_sources.json` (accept-list misconfiguration precondition) -> attacker forges a pack with no private key at all -> `import_propagation_pack` passes sig check, fingerprint binding, AND accept-list -> tombstone applied at destination -> `recover()` removes the victim record (bystander records untouched). Control: with an empty/absent accept-list the same forged pack is typed-rejected (fail-closed holds). For receipts, an identity-pubkey receipt with REAL content passes default `verify_receipt` with no secret at all - but that changes nothing over the documented self-anchored ceiling (any self-generated keypair already forges self-consistent receipts; see surface 6). Honest context: the limitation is DISCLOSED in the `_ed25519` module docstring ("not a complete RFC 8032 implementation... a hostile pubkey still reaches checkvalid before the accept-list gate runs"), and the accept-list is the designed trust anchor. Blast radius without operator misconfiguration: none observed. Fix: reject non-canonical encodings (y >= q) and small-order points in `_decode_point`/`checkvalid` (or use cofactored verification with order check), and validate on-curve/non-small-order at `authorize_source`.
Evidence: `probe2b` output line `PASS CHAIN identity-pubkey pack (zero private key) IMPORTS: victim record removed, bystander kept | remaining=['bystander']`; `probe1` C1/C2 (`checkvalid(identity-sig, msg, ID_PUB) -> True`).

**W2 (surface 1, LOW). `ensure_keypair` silently REGENERATES the root identity on key loss.**
`mbcp/attestation.py:190-203`: `load_keypair` returns None for a missing key file, and `ensure_keypair` mints a NEW keypair - identical to first-use. If `.mbcp.key` is lost/deleted, the next signing op (delete/export) silently switches identity: old receipts (old key_id) and new receipts (new key_id) BOTH verify `ok:True` under self-anchored `verify_receipt`; a third-party verifier anchoring on the original pubkey silently loses the tail; no event, flag, or log line distinguishes "first use" from "key loss". Rotation is documented as DEFERRED (SPEC 1.2.6); silent regeneration on LOSS is adjacent-but-undocumented (docstring says "creating it on first use" - key loss is not first use). Probe1 H1/H2: after `.mbcp.key` removal, `svc.delete()` succeeded and wrote a receipt under a brand-new key_id; both receipts verify ok.
Fix: on `load_keypair() is None` where a receipt/journal already exists, refuse (or require explicit rotate API) rather than mint silently.

**W3 (surface 1+2, LOW). Accept-list values are not validated; `authorize_source` raises untyped ValueError.**
`mbcp/attestation.py:309-345` `load_authorized_sources` accepts any string as pubkey_hex (probe2b #7: non-hex 64-char value loads fine); `authorize_source` (:348-368) raises RAW `ValueError` (not AttestationError) for key_id/pubkey fingerprint mismatch (:362) and for non-hex pubkey (:361, `bytes.fromhex`). Intake stays fail-closed regardless (probe2: a listed-but-bogus pubkey makes every pack fail the sig check with typed AttestationVerifyError). Defense-in-depth gap only.

**W4 (surface 3+7, LOW). `record_pending_propagation` is an unauthenticated, unlocked, unbounded append channel.**
`mbcp/propagation.py:487-522` (gate: signature-only via `_verify_pack_signed_only` :525-546; NO accept-list, NO schema check) appends to `propagation.jsonl` via `_append_propagation_line` (:733-741) with no lock, no authentication, no rate/size cap. Deliberate per SPEC 1.2.3 note and probe-verified NOT a laundering channel: `verify_receipt` never consults the journal, and `retry_pending_propagation` re-verifies sig + accept-list + digest chain + tombstone integrity before importing (probe3: hostile pending lines produce typed rejects at retry; no receipt divergence). Residual exposure: unbounded journal growth / churn from any in-process caller (availability, writer-root trust domain). Same trust domain as the writer, so rated LOW.

**W5 (surface 7, LOW). `retry_pending_propagation` except-tuple misses `DeletionError` -> raw crash, contract violation.**
`mbcp/propagation.py:598` catches `(PropagationError, AttestationError)` only. A typed `DeletionError` raised by `service.recover()` inside `_import_propagation_pack_locked` (e.g. corrupt destination bundle manifest) propagates RAW out of `retry_pending_propagation` and NO pending line is appended - violating the function's own contract ("on failure a new line is appended", docstring :571-573). Probe7 P6: corrupt `bundles/cb.json` -> `retry` raised raw `DeletionError`.

**W6 (surface 7, LOW). `retry` KeyError('retry_count') on retry-after-ack when import now fails.**
`mbcp/propagation.py:600`: `previous = entries[-1]["retry_count"] if entries else 0` assumes the last journal line for the pack is a PENDING line. ACKED lines (:476-482) carry no `retry_count` key. If a pack was imported (acked), the source is later deauthorized, and `retry` is called with the same pack, import raises `AuthorizationRejectedError` (AttestationError subclass, caught) and the except branch then does `entries[-1]["retry_count"]` on the ACKED line -> RAW `KeyError: 'retry_count'`. Probe7 P5. Fix: `entries[-1].get("retry_count", 0)`.

**W7 (surface 7, LOW). Schema-invalid but self-consistently SIGNED pack -> raw KeyError at enqueue and retry.**
`_verify_pack_signed_only` (`mbcp/propagation.py:525-546`) checks ONLY the ed25519 attestation; it never validates the pack body against the schema. `record_pending_propagation` (:511-521) and `retry_pending_propagation` (:583-584) then index `body["pack_digest"]` / `body["source_root"]` unguarded. Probe7 P7: a minimal signed pack `{pack: {key_id, attestation_pubkey}}` (valid signature, no schema) reaches `record_pending` -> RAW `KeyError: 'pack_digest'` (and same at retry). Fix: schema-validate the pack body inside the signed-only gate, or guard the keys.

**W8 (surface 7, LOW). Dead-letter is not terminal against re-enqueue.**
SPEC 1.2.8: "dead-lettered entries are terminal". `retry_pending_propagation` enforces this (`mbcp/propagation.py:588-595`, typed DeadLetterPropagationError - probe7 P3b). But `record_pending_propagation` (:487-522) has NO terminal-state check: re-enqueueing a dead-lettered pack appends a fresh PENDING line, and the next `retry` proceeds past the dead-letter gate (probe7 P4: status sequence dead-lettered -> pending -> import re-attempted). Same trust domain as the writer (who could also just delete the journal), so LOW; but it contradicts the SPEC's "terminal" wording. Fix: refuse re-enqueue when the last line for the pack_digest is dead-lettered.

**W9 (surface 1+5, LOW). Untyped build-path crashes on hostile inputs.**
`build_receipt` (`mbcp/deletion.py:399-493`) computes `canonical_sha256(tombstone)` at :446 BEFORE any validation: a tombstone with a lone-surrogate `target_id`/`reason` -> raw `UnicodeEncodeError`; NaN `reason` -> raw `ValueError` (json allow_nan=False). `sign_envelope` (`mbcp/attestation.py:206-244`) likewise raises raw ValueError on NaN bodies. Probe9 M1-M3. Build paths are trusted-operator paths (schema gates protect the load/verify paths), so LOW.

**W10 (hardening, LOW). `.gitignore` does not list `.mbcp.key` (private seed file).**
Repo-root `.gitignore` contains only `.secrets/`, `__pycache__/`, `*.pyc`, `.venv/`. The private key file (`KEY_FILE_NAME = ".mbcp.key"`, `mbcp/attestation.py:50`, written 0600) is not git-protected - a contributor adding the root dir could commit the seed. (`git ls-files` confirms none is tracked today.) Fix: add `.mbcp.key` (and `.mbcp.lock`, `.mbcp.authorized_sources.json`) to `.gitignore`.

### HONESTY-GAP (docstring/spec/commit claim contradicts code)

**H1 (surface 1, LOW). `load_keypair` docstring promises typed reject for "bad lengths"; wrong-LENGTH hex escapes as bare ValueError.**
Docstring `mbcp/attestation.py:157-161`: "bad lengths ... raises the typed AttestationError". Code: the try/except at :173-177 wraps only `bytes.fromhex` (odd-length/non-hex -> typed, correct); a valid-hex WRONG-LENGTH seed/pubkey passes `fromhex` and reaches `KeyPair(seed, pubkey)` at :178, which raises a RAW `ValueError` (probe1 F2: 31-byte seed -> untyped ValueError). Fix: move the KeyPair construction into the try, or validate lengths explicitly.

**H2 (surface 5/doc, LOW). SPEC.md:64-65 garbled sentence asserts put_bundle is NEVER under the lock.**
SPEC.md lines 64-65 read: "...per-thread held count, and never\n> `put_bundle` and propagation export ... are also under the lock for their full duration". As written, the first clause says put_bundle is never locked - contradicting the very next clause AND the code (`mbcp/deletion.py:586-595` put gate runs inside `_RootLock`; probe3 runtime matrix: put blocks+times-out under a held lock). Spec-lag typo; code is correct.

**H3 (surface 5/doc, LOW). SPEC.md:55 says supersession has exactly ONE trigger; code has TWO.**
SPEC 1.2.2: "Supersession 只有一個觸發位" (retry under-report). Code: retry-underreport (`mbcp/deletion.py:1087`, `reissue_on_id_collision=True`) AND the A-1 id-collision reissue on fresh-path delete (`mbcp/deletion.py:1217` default False, :1242-1246 reissue logic). Spec-lag (BACKLOG ADV-C3-3 closed the behavior; SPEC text not updated).

**H4 (surface 4/doc, LOW). SPEC.md:40 write-boundary wording says "(id, integrity.digest) pairs"; code is id-level (stricter).**
Code (`mbcp/deletion.py:586-595`, `mbcp/tombstone.py:136-146`) rejects ANY copy of a tombstoned id regardless of digest (digest-independent, probe4). Spec under-describes; safe direction.

**H5 (surface 5/doc, LOW). SPEC 1.5 "all comparisons normalize" vs two EXACT compares in the receipt layer.**
`mbcp/deletion.py:1577` (supersession chain-walk `target_id`) and `mbcp/deletion.py:1300` (`_latest_receipt` `bundle_id`) compare verbatim. Conservative direction (exact can only reject more; probe5 WG4/WG5 confirmed both behaviors), but the spec sentence is not uniformly true.

**H6 (surface 7/doc, LOW). `next_attempt_at` is computed but never enforced.**
`mbcp/propagation.py:504` docstring: next_attempt_at records "when the next retry becomes eligible". `retry_pending_propagation` (:556-616) has NO eligibility gate - a pending line with `next_attempt_at` in 2099 retries immediately (probe7 P8). Backoff is advisory-only. Either enforce or fix the docstring.

**H7 (doc, LOW). SECURITY.md still describes the pre-L4 world.**
`SECURITY.md:14-18`: "digest-chain integrity only", "無簽名（直到 L4 ed25519 落地）", "attestation gate... digest-chain 層面". L4 landed (commit 0fbe0e2; receipts/packs are ed25519-signed; `mbcp/attestation.py` exists). SECURITY.md predates the landing and was not updated.
